# DMFT 输入参数分类与处理规则

本文整理 `src/para/input.h` 和 `src/para/input.cpp` 后续重构所需的参数分类。按取值来源划分四个基本类别，再分别描述生效条件、相互约束和求值时机，避免把各种组合扩展成大量类别。

本文中的“当前实现”以现有代码为依据；“建议规则”和“设计示例”用于后续设计，不表示程序已经支持。输入格式、单位和物理公式保持不变；默认策略的明确变更是取消 nominal 模式下 `nf=1.0` 的默认值，改为条件必填。具体参数说明另见 [list_of_parameters.md](list_of_parameters.md)，其中历史说明仍需与代码核对。

## 一、按取值来源划分的四类参数

| 类别 | 用户能否指定 | 未指定时的行为 | 典型用途 |
| --- | --- | --- | --- |
| 1. 条件必填参数，无默认值 | 能 | 必填条件成立时，缺失则报错；条件不成立时不要求填写 | 无法合理推断的必要输入 |
| 2. 有默认值的参数 | 能 | 使用预先约定的默认值 | 常规计算选项和控制参数 |
| 3. 纯派生参数 | 不能 | 根据其他已确定的数据计算 | 必须满足物理关系或内部约定的量 |
| 4. 可由用户覆盖的自动参数 | 能 | 根据其他已确定的数据计算默认值 | 自动选取、但允许用户调整的计算设置 |

这里的“类型”指取值规则，与整数、浮点数、字符串、枚举、数组等数据类型相互独立。

### 1. 条件必填参数，无默认值

每个此类参数都有明确的必填条件。条件成立时，必须由用户显式提供，程序不使用默认值补齐；缺失时应说明参数名、必填原因及适用条件。条件不成立时，不要求填写。

无条件必填是必填条件恒为 `true` 的特例，无需另设类别。这里的 `true` 描述必填规则，不是参数的默认值。

当前 `nf` 属于第 1 类：选择 `double_counting nominal` 时必须显式提供，无默认值。其他参数不能仅凭看起来重要就改成必填，例如 `dft_solver` 仍默认是 `aims`。

必填条件与生效条件应分别描述：前者决定何时必须显式填写，后者决定何时参与计算；两者可以相同，但不能相互替代。

### 2. 有默认值的参数

用户输入优先；未输入时采用规定的默认值。固定默认值应集中定义，避免读取、日志和文档中分别维护。

当前例子：

- `temperature` 默认 `300 K`。
- `projector` 默认 `nao`。
- `mc_step` 默认 `5000000`。
- `projection_window` 默认 `-5.0 5.0`。
- `restart` 默认 `1 1 1 1`。
- `local_symmetry` 默认 `0`；`1` 为立方对称处理，d 壳层下 `2` 选择 t2g，`3` 选择 eg。

默认值也可以按后端或计算模式选择，称为“条件默认值”。它仍是预先规定的默认策略，不必单独设立基本类别。

### 3. 纯派生参数

该参数由其他参数或外部数据唯一确定，不作为独立的 `DMFT.in` 关键词。计算前必须确认依赖数据有效；用户直接输入时应明确提示它不是可输入参数。

当前例子：

- `beta` 由温度计算，内部单位是 `Hartree^-1`：`beta = Hartree_to_eV / (temperature * K_BOLTZMAN_EV)`。
- `n_tau` 由 `int(25 / (temperature * K_BOLTZMAN_EV))` 得到，若为奇数则加一。
- `n_omega` 由 `int(100 / (PI * temperature * K_BOLTZMAN_EV))` 得到，若为奇数则加一。
- `flag_restart` 由 `start_charge_step > 1` 或 `start_DMFT_step > 1` 判断。

这里 `K_BOLTZMAN_EV` 的单位是 `eV/K`，两个网格公式中的能量尺度分别为 `25 eV` 和 `100 eV`。重构应保留现有截断及偶数调整顺序。

`flag_restart` 是内部派生状态；输入关键词 `restart` 本身接受四个整数，两者不能混为同一个输入值。

### 4. 可由用户覆盖的自动参数

也称“支持自动默认值的可输入参数”。未指定时，从其他参数计算或复制默认值；显式指定时采用用户值，但仍须满足参数约束。

当前例子：

- `dos_window` 未指定时取 `projection_window`；显式指定后仍要求覆盖投影窗口。
- `dmft_step_first` 未指定时取 `max_dmft_step`。

建议独立记录“用户是否显式指定”，不能用 `0`、`-1` 或“恰好等于默认值”来判断。输入行的先后顺序不应影响自动默认值。

`n_tau` 和 `n_omega` 今后可以考虑从第 3 类改为第 4 类，但当前不支持直接输入。开放时需另行确定数值范围、偶数要求及求解器约束。`beta` 则不适合在保持温度不变时被任意覆盖，否则会破坏物理关系。

## 二、与四类取值规则交叉的条件和约束

### 第 1 类参数的必填条件

第 1 类统一按条件必填处理：必填条件可以依赖计算模式、后端或其他已确定的配置，也可以恒为 `true`。应在依赖配置确定后检查用户是否显式提供，不能仅检查成员变量是否已有数值。

当前 `nf` 的必填条件和生效条件均为 `double_counting=nominal`。其他模式不要求填写；显式填写时仍检查数值格式，但不参与计算。旧默认值 `1.0` 已取消。

需区分“必须显式输入”和“最终必须有有效值”：后者可以由默认值满足，前者不能。

### 条件默认值

根据计算模式、后端或求解器，从预先规定的默认值中选择。

设计示例：不同杂质求解器使用不同的默认采样步数。当前 `mc_step` 使用统一默认值，这个例子不表示已有按求解器分支的默认策略。

它通常归入第 2 类；若默认值由依赖参数通过公式计算或直接复制，则归入第 4 类。实现上两者都应在依赖选项确定后处理，不必为了分类边界增加复杂机制。

### 互斥输入、择一输入与一致性约束

多个输入可能表达同一物理自由度，或选择相互排斥的功能。应为每组参数明确规则：

- 至多一个：允许都不提供，但不能同时提供。
- 恰好一个：必须提供其中一个，不能同时提供。
- 可以同时提供：必须检查两者是否一致，并约定数值容差。

设计示例：如果未来同时支持 `temperature` 和 `beta`，可要求只输入一个，或者同时输入时检查热力学关系。不能默认以后出现的值覆盖前一个。当前程序只接受 `temperature`，`beta` 是纯派生量。

这与第 4 类不同：第 4 类允许调整自动选取的设置；同一物理量的不同表达则必须保持一致。

### 生效条件

参数可以有合法值，但只有在特定模式下才参与计算。当前例子：CWF 窗口设置用于 `projector=cwf` 的情形；ComCTQMC 的五个启动与采样参数只在 `impurity_solver=comctqmc` 时参与计算和输出。

建议明确区分“未填写且当前不需要”和“用户显式填写但当前不生效”。对后者提示未生效；若组合本身不允许，则报错。不要静默让用户误以为设置已被采用。

### 跨参数约束

即使各参数单独合法，组合也可能不合法。

当前例子包括：

- `dos_window` 必须覆盖 `projection_window`。
- 使用 CWF 时要求 `cwf_ep0 < cwf_ep1` 且 `cwf_t > 0`。
- 选择 DFT 后端时需检查程序是否编译启用了对应支持。

约束检查不能被用户覆盖默认值的行为绕过。

## 三、依赖外部数据与求值时机

有些量依赖 DFT 输出、结构文件或重启文件，不能只通过 `DMFT.in` 确定。设计上的例子包括费米能、轨道数和自旋通道数；这不意味着应将这些量全部搬进 `input_info`。

按取值来源，它们可以属于纯派生参数，或在允许覆盖时属于第 4 类；额外需要说明：

- 数据来源，以及负责读取或计算的模块。
- 在哪个阶段才能确定。
- 哪些检查必须等到外部数据就绪后执行。
- 若允许用户指定，如何检查它与外部数据的一致性。

仅依赖输入参数的默认值和派生量，可在输入初始化阶段处理；依赖外部数据的量留到对应初始化阶段。无需强行让 `read()` 完成所有计算。

## 四、兼容名称、废弃参数与运行状态

### 兼容别名

别名不是新的取值类别。读取时将别名规范化为同一个内部选项，再检查重复和冲突，输出使用统一名称。

当前例子：`projector=default` 是 `projector=nao` 的兼容写法；`hyf_dc_mode` 也接受部分选项别名。

### 废弃或未生效的历史参数

应区分“仍然有效的旧写法”“已废弃但暂时接受”和“已不再支持”。不能仅因为关键词在白名单里，就认为它具有实际作用。

当前兼容处理：`dft_solver_exe` 和 `hybrid_xc_coeff` 仍被接受，但输出未生效警告。`local_symmetry` 属于第 2 类，默认 `0`，由 `input_info::read()` 统一读取并保存到参数结构体；原子模块通过 `in.get().local_symmetry` 取得配置，保留用于轨道构建及对称化的副本。它不是从 DFT 输出推导的量；`symmetry.dat` 的原子等价关系仍单独读取。

### 可变运行状态

迭代中的当前步数、收敛状态等不属于上述输入参数类别，应由运行模块维护。`restart` 提供的初始步数属于输入配置，不能与运行中不断更新的步数混用。

## 五、后续实现应记录的信息

每个参数应能够明确回答以下问题；这些信息可以分别体现在简单的定义表、校验代码和文档中，不要求建立完整注册框架。

| 信息 | 内容 |
| --- | --- |
| 名称与数据类型 | 规范名称、兼容写法、值个数、整数/浮点数/选项等 |
| 物理约定 | 单位、能量参考点及必要的数值约定 |
| 取值来源 | 上述四类之一，默认值或自动计算规则 |
| 显式输入记录 | 用户是否提供 |
| 条件和约束 | 必填条件、生效条件、允许值、互斥及跨参数关系 |
| 依赖和时机 | 依赖哪些参数或外部数据，何时求值 |
| 最终输出 | 生效值及来源：用户输入、固定/条件默认、自动默认或纯派生 |

建议处理顺序为：设置固定默认值 → 单次读取并记录显式输入 → 检查必填项和基本合法性 → 补齐条件及自动默认值 → 检查跨参数约束 → 计算纯派生量并检查结果 → 输出最终参数。涉及外部数据的步骤在数据就绪后执行。

第一轮重构应保持现有有效输入的默认值、单位及派生公式不变；新增必填项、开放网格参数覆盖或改变兼容策略，应作为明确的行为变更单独验证。

## 六、input.cpp 的处理流程及备注

### 当前执行方式

`read()` 已实际整理为六个阶段，每个阶段入口都有备注：

1. 为第 2 类设置固定默认值。
2. 一次读取文件，记录显式输入；先转换第 2 类，再读取第 1 类及第 4 类的显式值。第 3 类不接受独立输入。
3. 补齐第 4 类 `dos_window`、`dmft_step_first` 的依赖默认值。
4. 检查第 1 类必填条件，以及第 2、4 类的取值和跨参数约束。
5. 计算第 3 类 `beta`、`n_tau`、`n_omega` 和 `flag_restart`。
6. 集中输出最终参数。

第 4 阶段检查 `nf` 的条件必填规则：nominal 模式缺失 `nf` 时报错。新增了严格数值转换、重复和未知关键词检查，以及温度为正和网格整数溢出检查；除取消 nominal 模式下 `nf=1.0` 的默认值外，已有公式、选项映射、单位及其他默认值保持不变。日志数值精度改为 12 位有效数字，`projector=default` 在日志中统一显示为规范名 `nao`。

相对 develop 新增的拒绝规则（此前被静默接受）：

- 数值关键词含非法文本时退出，不再由 `atoi/atof` 静默转成 0。例如 `temperature abc` 在 develop 上得到 `temperature 0`，会使 `beta` 发散。
- 同一关键词重复出现时退出；develop 取首次出现的值。
- 未知关键词退出，判定范围与 `read()` 实际消费的关键词一致。

`interaction_type`、`comctqmc_nproc`、`warmup`、`comctqmc_exe`、`comctqmc_evalsim`、`comctqmc_launcher`、`projection_min_weight` 以及 `impurity_solver=comctqmc` 均沿用 develop 的默认值、生效条件与校验。ComCTQMC 的五个关键词在任何求解器下都被接受，取值和日志只在 `impurity_solver=comctqmc` 时生效。

所有输入参数统一读取；重复扫描文件的 `read_parameter()` 和 `atoms_info::read_local_symmetry()` 已删除，不再通过抛出 `bool` 表示参数缺省。旧 `parameter()` 字符串分发及 `const void*` 接口已删除，参数集中保存在 `input_parameters` 结构体中，保留四类分组；`input_info` 私有持有该结构体，通过唯一的 `const input_parameters& get() const` 返回只读引用。例如 `in.get().temperature`、`in.get().max_dmft_step`，字符串和窗口也直接通过成员读取，不再逐参数定义 getter。读取、默认值补齐和校验仍由 `input_info::read()` 负责。下游无需手动转换指针类型。遗留的 `input_info::test()` 和 `input_info::out()` 已删除，`parameters::out()` 中的对应调用也已移除；输入校验和最终参数日志由 `read()` 负责。

下面七步描述更完整的后续设计，其中来源标注、统一参数定义表、新增物理约束尚未全部实现；类型明确的只读访问接口已完成。

### 建议整理后的执行步骤

以下步骤按依赖顺序执行。函数名称和具体拆分可以在实现时确定，不要求每一步都新增一个类或通用框架。

#### 步骤 1：初始化固定默认值和输入记录

为第 2 类参数设置固定默认值；清空显式输入记录，为本次读取准备干净的状态。

备注：必填参数不能用一个看似合法的默认值掩盖缺失；纯派生量不在这里求值。若支持重复调用 `read()`，不能遗留上次读取的窗口、显式输入标记或派生结果。

#### 步骤 2：单次读取文件，解析用户输入

逐行读取 `DMFT.in`，处理空白和注释，识别关键词，检查值个数，再转换为对应类型。规范化受支持的关键词及选项别名，并记录用户显式提供的参数。

备注：只对约定不区分大小写的关键词和选项做规范化，不能任意改变路径等字符串。未知关键词、重复关键词、数值格式错误和溢出应在此处报告；不要用 `atoi/atof` 将非法文本静默转成零。参数缺失是正常的待处理状态，不应靠抛出 `bool` 表达。

#### 步骤 3：检查必填项和基础合法性

在计算模式等选项确定后，检查第 1 类参数的必填条件；条件成立时要求显式输入，包括条件恒为 `true` 的情形。同时检查允许的选项、后端编译支持，以及已确定数值的基本约束，例如温度必须为正。

备注：“必须显式输入”通过输入记录检查，不能仅检查成员变量是否有值。对于尚待自动补齐的参数，完整的取值检查留到补齐之后。若某个条件依赖自动默认值，也应等依赖就绪后再检查。

#### 步骤 4：补齐条件默认值和自动默认值

按依赖顺序处理未被用户指定的参数。例如，先确定 `projection_window`，再设置缺省的 `dos_window`；先确定 `max_dmft_step`，再设置缺省的 `dmft_step_first`。

备注：仅在“未显式指定”时补齐，不根据值是否为零判断。用户值优先，但不能绕过后续合法性检查。输入文件中的行顺序不得影响最终值；依赖顺序应在代码中直接写清，不需要自动依赖图。

#### 步骤 5：检查完整配置及跨参数约束

对补齐后的所有相关参数执行检查，包括数值范围、窗口顺序、DOS 窗口覆盖投影窗口、互斥或一致性规则，以及特定模式的约束。识别用户显式填写但当前未生效的设置。

备注：使用 CWF 时检查 `cwf_ep0 < cwf_ep1` 和 `cwf_t > 0`；具体范围及求解器限制以算法要求为准，不能凭经验随意加入新限制。未生效参数应按已确定的策略提示或报错。首轮重构中新增的拒绝规则需明确记录，不能视为完全无行为变化。

#### 步骤 6：计算纯派生量并检查结果

在依赖通过校验后，计算 `beta`、`n_tau`、`n_omega` 和 `flag_restart`。检查派生结果是否满足后续算法要求。

备注：保留现有温度与能量单位、整数截断及奇数加一的顺序。网格计算还需在转换为整数前检查可表示范围，避免极端温度导致溢出。若将来允许手动设置网格，应移入步骤 4 的自动默认值处理，仅在未指定时使用公式。

依赖 DFT 输出、结构或重启数据的派生量，在对应数据就绪后由相关模块计算和检查，不强行放入 `read()`。

#### 步骤 7：输出最终参数，交给计算模块

统一记录最终生效值、单位和来源，区分用户输入、固定或条件默认、自动默认以及纯派生值。成功完成后通过 `get()` 返回的参数结构体常量引用提供给后续计算（已实现）。

备注：不覆盖原始 `DMFT.in`，不在默认值尚未补齐时打印“最终参数”。采用足够的数值精度，并明确未生效项。初始化未通过时应停止进入求解流程，不能让其他模块使用半初始化配置。运行中的迭代状态仍由求解模块维护。

### 修改边界

本次已重组 `read()` 并替换主解析流程，下游已迁移至类型明确的只读访问接口；未开放 `n_tau/n_omega` 手动输入，除已取消的 nominal 模式 `nf=1.0` 默认值外，其余物理默认值不变。后续继续完善参数来源日志时，应保持已有有效输入的数值结果一致。

### 与 develop 的同步要求

本分支最初基于 `init`，而 `interaction_type`、ComCTQMC 相关参数和 `projection_min_weight` 是之后经 `general-interaction` 并入 develop 的。rebase 时若只合并 `input_parameters` 的成员及 `get()` 下游调用、却漏掉 `input.h` 的成员声明和 `read()` 的解析块，会直接编译失败；更隐蔽的情况是成员仍声明但不再赋值，下游读到未初始化值而不报错。

因此每次 rebase 后必须核对三处一致：`input.h` 的成员声明、`read()` 的赋值与 `recognized` 集合、`input_parameters` 的成员及 `get()` 下游调用。

`dmft_step_first` 曾被误删，现已恢复。它在 `init` 中存在，用于让首个电荷循环采用不同于 `max_dmft_step` 的 DMFT 步数上限：首轮从 KS 密度出发、自能远离收敛，需要更多步；后续循环密度只被微调，可少跑以节省 QMC 采样。未指定时取 `max_dmft_step`，因此默认行为与无此参数一致。

追溯 git 对象可知它不是被有意废弃的：`main` 是一条独立历史（空根 `Initial commit` → `Import uncompiled DMFT source snapshot from DF server`），导入的 DF 服务器快照本身就缺这一行声明；随后的 `Normalize text file line endings to LF` 只做 CRLF→LF 转换，未恢复内容。合并提交 `96d6ea02`（Merge branch 'main' into merge-main-at-init）两侧**没有共同祖先**，每个文件都是 add/add 冲突，解决时三个文件的 blob 被整体取成 main 侧，功能就此丢失；4 分钟后的 `45716978` 又对 `general-interaction` 侧重复了同样的丢弃。

由此得到一条通用要求：本仓库存在无共同祖先的历史合并，冲突必须逐块核对两侧内容，不能整文件取一侧。整侧取舍会静默丢弃另一侧的功能，且编译期未必报错——`dmft_step_first` 丢失后 `solver.cpp` 的循环上界被一并改写，程序照常编译运行，只是首轮不再享有更多步数。
